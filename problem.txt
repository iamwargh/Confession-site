[CRITICAL] AUTH-1 — PKCE callback redirects to wrong URL in production
File: web/src/app/auth/callback/route.ts (Line 48, 91)
-----------------------------------------------------------------------
PROBLEM:
  When a user confirms their email, the callback redirects using the
  `next` param: `${siteUrl}${next}`. But the `next` default is `'/'`.
  This is fine locally, BUT if NEXT_PUBLIC_SITE_URL is not set in
  Vercel, `siteUrl` falls back to `origin` (which is the request origin
  — could be Supabase's internal URL in some edge cases).

  Also, after a PKCE code exchange for a NEW signup, the user is
  redirected to `/` (home) without any welcome message or prompt.
  They may not realize they're now logged in.

IMPACT: Users may be redirected to wrong URL or land silently on home
page without confirmation they are verified.

FIX:
  - Ensure NEXT_PUBLIC_SITE_URL is set in Vercel environment variables.
  - After successful signup verification, redirect to
    `/login?verified=true` or `/` with a toast notification.

[CRITICAL] AUTH-2 — No middleware.ts file — proxy.ts is NOT auto-loaded
File: web/src/proxy.ts
-----------------------------------------------------------------------
PROBLEM:
  Next.js middleware MUST be in `src/middleware.ts` (or project root
  `middleware.ts`). The file is named `proxy.ts`, so Next.js NEVER
  automatically runs it. All route protection (auth guards, role checks,
  suspension checks) is completely bypassed.

  The file exports a `proxy` function and a `config` object, but
  Next.js will not pick this up because it is not named `middleware.ts`
  and the export is not called `middleware`.

IMPACT: CRITICAL security hole — ALL protected routes (/admin,
/superadmin, /post, /my-confessions, /account) are publicly accessible
without authentication. Anyone can browse them without being logged in.

FIX:
  Create `web/src/middleware.ts` that imports and re-exports from
  proxy.ts:
    import { proxy as middleware } from './proxy'
    export { middleware }
    export { config } from './proxy'
  OR rename proxy.ts → middleware.ts and rename the export `proxy` to
  `middleware`.

[HIGH] AUTH-5 — forgot-password: uses `window.location.origin` in SSR
File: web/src/app/forgot-password/page.tsx (Line 27)
-----------------------------------------------------------------------
PROBLEM:
  Line 27:
    `${process.env.NEXT_PUBLIC_SITE_URL || window.location.origin}/reset-password`
  
  `window` is not defined on the server. Although forgot-password is a
  client component ('use client'), if there's any SSR pre-render pass,
  this will throw "window is not defined".

  The same pattern exists in signup/page.tsx (Line 99) and login/page.tsx
  (Line 109) — all three components build `siteUrl` using
  `window.location.origin` as a fallback, but they wrap it with
  `typeof window !== 'undefined'`. The forgot-password page does NOT
  have that guard. It passes `window.location.origin` directly into
  the function call.

IMPACT: Runtime error "window is not defined" crash in SSR/edge runtime.

FIX:
  Change Line 27 to:
    `${process.env.NEXT_PUBLIC_SITE_URL || (typeof window !== 'undefined' ? window.location.origin : '')}/reset-password`

[HIGH] MW-2 — Suspension check in proxy runs on EVERY protected route visit
File: web/src/proxy.ts (Lines 126-174)
-----------------------------------------------------------------------
PROBLEM:

IMPACT: Noticeable slowdown on every authenticated page navigation.

[HIGH] CORE-1 — likes_count is manually synced — can go out of sync
File: web/src/lib/actions/confessions.ts (Lines 188-201)
-----------------------------------------------------------------------
PROBLEM:
  The `toggleLike` function manually:
  1. Inserts/deletes from the `likes` table
  2. Then fetches the current `likes_count` from `confessions`
  3. Then manually updates `likes_count`

  This is a race condition. If two users like the same confession at
  exactly the same time:
    - User A reads likes_count = 5 → writes 6
    - User B reads likes_count = 5 → writes 6
  Result: count is 6 instead of 7. Likes are silently lost.

IMPACT: Like count becomes inaccurate under concurrent use.

FIX:
  Use Supabase's RPC or atomic SQL increment:
    .rpc('increment_likes', { confession_id: confessionId })
  Or use raw SQL: UPDATE confessions SET likes_count = likes_count + 1

[MEDIUM] CORE-4 — reportConfession: uses .single() which errors on no rows
File: web/src/lib/actions/confessions.ts (Lines 234-240)
-----------------------------------------------------------------------
PROBLEM:
  When checking for an existing report:
    const { data: existing } = await supabase.from('reports')
      .select('id')
      .eq('confession_id', confessionId)
      .eq('reported_by', user.id)
      .single()
  
  `.single()` throws a Supabase error if there are no rows (PGRST116).
  This error is being silently swallowed (no error handling), but it
  means the `existing` variable will be null from an error, not a
  genuine "no match". The code correctly continues, but the error is
  logged to stdout as a noise error in Supabase logs.

FIX:
  Use `.maybeSingle()` instead of `.single()`:
    .maybeSingle()
  This returns null cleanly when there's no row.

  Same issue exists in toggleLike (Line 154) for existingLike check.

File: web/src/app/post/page.tsx (Line 14)

-----------------------------------------------------------------------
PROBLEM:
